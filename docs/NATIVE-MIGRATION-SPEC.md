## 기술 결정 (조사로 확정한 것)

| 항목 | 결정 | 근거 |
|---|---|---|
| 언어 | Java 유지 | 현행 빌드가 Gradle 없는 수제 파이프라인(aapt2+javac+d8). Kotlin은 이 파이프라인에서 불가 |
| 암호 라이브러리 | Bouncy Castle bcprov jar 1개만 추가 | Keccak-256·secp256k1 서명(RFC6979)·HMAC을 전부 제공. Maven Central에서 직접 조달 가능함을 확인 |
| 네트워크 | 현행 Bridge의 HttpURLConnection 유지 | 이미 실전 검증됨. OkHttp를 새로 들일 이유 없음 |
| JSON | Android 내장 org.json | 단, 주문 본문은 L2 HMAC와 바이트 단위로 일치해야 해서 필드 순서를 고정한 수동 직렬화로 만든다 (SDK의 JSON.stringify 순서 재현) |
| 비밀 저장 | 현행 Bridge 방식 그대로 | Android Keystore AES-GCM, enc1: 형식 유지 — 마이그레이션 불필요 |
| 상태 저장 | bm_durable(SharedPreferences)를 정본으로 승격 | 돈 관련 키 7종은 이미 이중 기록 중. LS 전용 키(로그·stage·snap 캐시 등)는 네이티브 등가물로 대체 |

## 재현 리스크 (조사에서 특정된 것)

1. **JS double 의미론**: SDK 금액 산출(roundDown/roundUp)과 엔진의 roundTick이 배정밀도 double 연산이다. BigDecimal로 "정확히" 계산하면 경계값에서 결과가 갈릴 수 있다. 네이티브에서는 같은 순서의 double 연산을 재현하고, 경계값 케이스를 골든 테스트에 포함한다.
2. **주문 본문 바이트 일치**: POST /order 본문 JSON의 필드 순서가 L2 HMAC 대상 문자열과 일치해야 한다. SDK의 직렬화 순서를 고정 문자열로 재현한다.
3. **dex 메서드 수**: bcprov jar가 크다. 1단계에서 빌드에 넣어 d8 통과와 단일 dex 여부를 먼저 확인한다. 초과하면 필요한 클래스만 추리는 방식으로 바꾼다.
4. **RPC 폴백**: viem transport는 사실상 로컬 서명 전용이었고 실제 RPC는 엔진의 수작업 rpcCall(4개 엔드포인트 폴백)이 담당 — 이 구조 그대로 이식한다.

## 이관 단계 (검증 단위별)

| 단계 | 내용 | 게이트 (통과 못 하면 다음 단계 금지) |
|---|---|---|
| 1. 암호 코어 | Keccak-256, ABI 인코딩, EIP-712(hashStruct/hashDomain), POLY_1271 래핑 서명, L1 서명, L2 HMAC, CREATE2 funder 파생, Batch 서명 | 골든 테스트: 고정 개인키·고정 입력으로 네이티브 출력이 SDK 출력과 바이트 단위 일치 (주문 서명·L1·Batch·금액 산출 경계값 포함). 빌드에 jar를 넣고 APK 빌드 성공 — **완료 (38/38)** |
| 2. 읽기 경로 | Gamma/Data/CLOB 조회 클라이언트, 장부 집계(summarizeBook), 스냅샷·사이징 | fixture 대조 200 체크 통과 — **완료**. 실기기 섀도우 대조는 개정으로 생략 |
| 3. 판정 이식 | 스캔 필터, 후보 검증, 손절 판정, 리딤 계획·정화 판정을 네이티브로 이식 | engine.js 원본 함수를 추출 실행해 만든 fixture와 전 케이스 일치 |
| 4. 쓰기·전환 | 주문 제출, 손절 매도, 리딤 제출을 네이티브로 이식하고 사이클 루프를 네이티브 스레드로 전환, JS 엔진 비활성화 | 서명·본문 골든 대조 통과 + 전환 후 첫 사이클 제출 결과 즉시 확인. 롤백은 직전 버전 APK 재설치 |
| 5. UI·마무리 | 화면 네이티브화(상태·평가금·사이징·리딤 키·로그·업데이트), 자동 제보 감지 3종 이식, SelfUpdate 유지 | 실기기 24시간 무중단 사이클 + 제보 감지 동작 확인 후 웹뷰·JS 번들·구 코드 삭제, 한 버전으로 출시 |

구 엔진(JS)은 4단계 전환 전까지 그대로 가동한다. 이관 작업이 운영 중인 매매를 멈추지 않는다.

## 프리모템 (실패 시나리오 3개와 차단책)

1. **서명이 바이트 단위로 안 맞아 전 주문이 거부된다** → 1단계 골든 게이트를 통과하기 전에는 쓰기 경로에 착수하지 않는다. 첫 실주문은 4단계에서 수동 확인으로만 낸다.
2. **금액 산출이 경계값에서 어긋나 과소·과다 주문이 나간다** → roundDown/roundTick 경계값 케이스(틱 경계 ±1ulp, 반올림 자리 경계)를 골든 세트에 넣고, 3단계 섀도우에서 네이티브 산출 금액과 JS 산출 금액을 전 후보 대조한다.
3. **이관 도중 구 엔진 장애가 재발해 매매 공백이 생긴다** → 구 엔진은 4단계까지 현행 v0.3.24 그대로 두고, 이관 코드는 별도 플래그 뒤에 둔다. 전환 후 이상이 보이면 플래그로 즉시 JS 경로로 되돌린다 (최종 5단계에서만 구 코드를 지운다).

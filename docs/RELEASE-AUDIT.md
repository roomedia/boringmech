# 출시 전 전면 감사 체크리스트 (2026-11-15 사용자 지시로 고정)

규칙: 매 릴리스마다 아래 4축 감사를 먼저 수행하고, 발견된 버그의 수리와
가드 테스트까지 전부 묶어 **한 버전**으로 낸다. 작은 수정을 여러 버전으로
쪼개 내지 않는다.

## 출시 게이트 (2026-11-19 사용자 확정)

출시 순서는 **감사 → 수정 → 출시**로 고정한다. 4축 감사를 전부 수행하고,
감사 발견이 남아 있으면 릴리스를 게시하지 않는다. 발견은 전부 수리 + 가드
테스트까지 마친 뒤에만 출시 단계로 넘어간다.

## 감사 축

1. **주문 실행** — 제출 잠금의 실제 이중 제출 차단, postOrder 결과 불명
   처리, 토큰·쪽(side) 매핑, 가격·수량·정밀도 계산, 검증 후 주문까지의
   가격 변동 방치 여부
2. **손절** — 판정 가격·부호·경계, 실행 순서(매수보다 먼저)의 전 경로
   보장, 실패·부분 체결·결과 불명 처리, 손절 후 재매수 차단이 정화에
   지워지지 않는지
3. **리딤·정화·장부** — 승자 리딤 누락 형태, 정화가 실체결 기록을 지우는
   경우, 장부 집계(open/정산/실현손익)가 슬롯·판단을 왜곡하는 경우
4. **스냅샷·사이징·수명주기** — 부분 실패 시 옛 값으로 매매 진행, 자본·
   현금 계산의 NaN·이중 계산, 사이클 중복 실행·단계 건너뜀, 저장 상태
   손상 시 기본값이 위험한 방향으로 떨어지는지

## 절차

1. 축별 적대 감사 (방어가 있다고 믿지 말고 코드로 검증)
2. 발견은 코드 대조·재현으로 확정한 것만 수리 대상
3. 수리마다 가드 테스트 추가, 전체 테스트 통과 확인
4. 발견이 0건이거나 전부 수리된 뒤에만 버전을 하나로 범프해 릴리스
   (발견이 남아 있는 상태에서는 릴리스를 게시하지 않는다)

## 빌드 산출물 게이트 (2026-11-15 추가 — v0.3.26~29 브리지 사망 사고)

릴리스 전 출하 APK의 dex를 직접 확인한다. 소스·테스트 통과만으로 내지 않는다.

- dex 문자열 테이블에 `Landroid/webkit/JavascriptInterface;`가 있어야 한다.
  없으면 브리지 메서드가 JS에 전혀 노출되지 않아 앱 전체가 무반응이 된다
  (keep.pro의 `-keepattributes *Annotation*`가 지킨다).
- 확인 명령: APK를 풀어 `strings classes.dex | grep JavascriptInterface`.

## 출하 dex 쓰기 경로 검증 게이트 (2026-11-19 추가 — v0.3.33 서명 VerifyError 사고, 상시 항목)

R8 enum unboxing이 Bouncy Castle `DefaultServiceProperties`의
`instanceof CryptoServicePurpose`를 원시 타입 `I`에 대한 instance-of로
바꿔, 서명 경로 전체가 실기기에서 VerifyError로 죽었다. JVM 테스트는
축소 전 바이트코드를 돌리므로 이 계열을 구조적으로 못 잡는다.

- `android/dex_gate.py`가 build.sh에서 서명 전에 상시 실행된다. 실패하면
  빌드가 중단된다. 검사 항목: ① 전체 dex에서 참조 타입 opcode
  (instance-of·check-cast·const-class·new-instance·new-array·
  filled-new-array(-range))의 원시 타입 참조 0건 — 2026-11-19 제보 37
  후속으로 instance-of·check-cast 2종에서 전수로 확장했다. 같은
  unboxing이 다른 opcode로 새면 통과한 채 출하되는 구멍이 있었다.
  ①b DefaultServiceProperties의 instance-of 대상에 CryptoServicePurpose
  포함 (instance-of가 남아 있는 경우) ② JavascriptInterface 존재
  ③ 쓰기 경로 앱 클래스
  (매수·손절·수동 매도·리딤 제출) 전부 존재 ④ 매핑 기준 서명 경로 BC
  클래스(DefaultServiceProperties·CryptoServicePurpose·Keccak·SHA256·
  ECDSASigner) 전부 존재 ⑤ 수명주기 앱 클래스(EngineService·
  MainActivity·외부 감시 리시버·스케줄러·판정) 전부 존재 — 매니페스트가
  가리키는 리시버가 축소로 사라지면 외부 감시가 조용히 무력화된다.
- 축소 코드 실행 스모크: `android/test/run_shrunk_smoke.sh`가 출하와
  같은 keep.pro로 R8 축소(classfile)를 돌려 그 바이트코드로 골든 38건
  (주문 서명 포함)을 실행한다. 릴리스 전 실행해 통과를 확인한다.
- keep.pro에 규칙을 추가할 때는 어떤 결함을 막는 규칙인지 주석으로
  남긴다. 근거 없는 keep 누적 금지.

## 서명 경로 실기기 검증 게이트 (2026-11-19 추가)

서명 경로 실기기 검증: 릴리스 후 실기기에서 실제 서명 제출 1회(수동
매도 등)가 성공 로그로 확인되기 전까지, 그 버전은 서명 경로 미검증
상태로 표기한다. 미검증 표기는 릴리스 노트와 보고에 명시한다. 실기기
검증이 실패하면 즉시 수리 버전을 낸다.

출하 dex 게이트·축소 스모크는 빌드 시점 검증이고, 실기기 검증은 그
다음 단계로 별개 항목이다. 둘을 혼동해 빌드 검증만으로 서명 경로가
검증됐다고 표기하지 않는다.

## 제보 로그 판독 규칙 (2026-11-19 추가 — 제보 37 오판 후속)

제보 payload의 로그는 누적 durable 로그의 최근 200줄 창이다. 같은
오류 줄이 여러 제보에 반복해서 실려도, 그게 각 버전에서 새로 발생한
것이 아니다. 오류의 발생 버전을 확정할 때는 반드시 로그 줄의 시각을
그 버전의 릴리스 시각과 대조해 구간을 나눈다.

- 사례: 제보 37(v0.3.35)의 14:15:08 VerifyError는 v0.3.34 릴리스
  (15:05)보다 앞선 v0.3.33 세션의 기록이 누적 창에 실린 것이었다.
  "3빌드 연속 동일 오류 출하"로 읽으면 이미 고쳐진 결함을 다시
  고치게 된다. 출하본 판정은 로그가 아니라 해당 APK의 dex를 직접
  열어 확인한다 (dexdump로 문제 클래스의 문제 오프셋을 대조).

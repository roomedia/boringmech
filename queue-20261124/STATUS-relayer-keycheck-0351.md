# v0.3.51 relayer 키 확인 — 상태

- 상태: awaiting (출시 완료 2026-11-25, 설치는 동호)
- 범위 확정: 사용자 결정으로 .51은 키 확인 단일 범위. 진입 시작 시각 조사는 문서·결론까지만 (entry-window-research-20261125.md, 판정 불가·현행 유지), 사이징 변경은 미착수 상태로 .52 이후로 분리.
- 과제: relayer 키 설정 UI에서 저장 직후 자동 1회 + "연동 확인" 버튼으로 인증 조회를 돌려 정상(200)/인증 실패(401)/확인 불가(기타)를 구분 표시. 저장은 막지 않는다.

## 설계 판정 (실측 근거)

- 당초 전제였던 params 조회(GET /v1/account/transactions/params)는 무인증 공개다 — 실측: 헤더 없음·가짜 키 모두 200. 키 검증 불가.
- tx 단건 조회(GET /v1/account/transactions/{id})도 무인증 — 가짜 키+없는 id에서 401이 아닌 404.
- 거래 목록 조회(GET /v1/account/transactions?address=…)가 인증 엔드포인트 — 실측: 헤더 없음 401, 가짜 키 401 ({"error":"invalid authorization"}), POST /submit 가짜 키도 동일 401. → 확인 호출은 목록 조회로 확정. GET 전용이라 제출을 만들지 않는다.
- 결과 분류: 200=정상, 401=인증 실패, 그 외(503·네트워크·시간 초과)=확인 불가. 기존 isRelayerAuthError 문구("relayer 조회 HTTP 401")와 정합.
- 상태 캐시: localStorage bm_relayer_check에 {지문 해시, status, 시각}만 저장 — 지문 원문(키 포함)은 저장하지 않는다. 자격증명이 바뀌면 해시 불일치로 자동 무효.
- 래치: 확인 401 → 같은 지문으로 제출 래치 설정 (제출 경로 401과 동일 의미). 확인 200 → 같은 지문 래치 해제. 확인 불가 → 래치 무접촉.
- 네이티브 패리티: 확인은 설정 UI 일회성 동작이라 JS만 구현. 네이티브 사이클은 자격증명 미러를 리딤 시점에 읽을 뿐이고, 확인이 쓰는 상태(JS 인메모리 래치·UI 캐시)는 네이티브가 소비하지 않아 충돌 없음.

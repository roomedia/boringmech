# relayer 401 리딤 실패 분석 (2026-11-25)

## 증상

- 제보 id 44 (v0.3.49), 사이클 294 (2026-11-25 08:22:38 KST)부터 매 사이클 리딤 제출이 실패한다.
  오류: `리딤 실패 0x043fac12…: relayer 제출 HTTP 401: {"error":"invalid authorization"}`
- 사이클 294에서 정산된 포지션이 생겨 보유가 8건에서 7건으로 줄었고, 그 건의 현금 회수가 막혀 있다.
- 제보 id 43 (v0.3.48)에는 리딤 시도 자체가 없다. 온체인 마지막 REDEEM은 2026-11-15로, Relayer API 키 등록 (2026-11-19)보다 앞선다. 그 사이 정산 건들은 전액 손실 종결 (온체인 잔고 0 확인 경로)이나 수동 매도로 닫혀 제출이 필요 없었다. **즉 이번 건이 키 등록 후 첫 relayer 제출 시도이고, 키 쌍이 실제로 검증된 적은 한 번도 없었다.**

## 원인 판정

**저장된 (API Key, 주소) 쌍이 이 계정의 유효한 소유자 쌍이 아니다. 자격증명 측 문제다.**

근거:

1. 앱 방식은 현행 공식 문서와 일치한다. 엔드포인트 `https://relayer-v2.polymarket.com`, 헤더 `RELAYER_API_KEY` + `RELAYER_API_KEY_ADDRESS`, 흐름 GET `/v1/account/transactions/params` → 서명 → POST `/submit` 전부 문서 규격 그대로다 (docs.polymarket.com relayer Submit a transaction, Wallets and Authentication).
2. 앱 회귀가 아니다. 제출 경로 (네이티브 RedeemSubmitter)는 v0.3.29 네이티브 전환 이후 무변경이고, v0.3.45~49의 diff는 이 경로를 건드리지 않는다 (.49 NativeCycle 변경은 손절 폴백뿐).
3. 실패 지점이 제출(POST)에서만 난다. nonce 조회(params)는 무인증 공개 엔드포인트라 키가 틀려도 성공한다. 키 검증은 첫 인증 호출인 POST /submit에서 이뤄지므로, GET 성공 후 POST 401은 "키 쌍 거부"와 정합한다.
4. 자격증명은 기기 금고에서 정상적으로 읽혔다. 읽기에 실패하면 앱은 제출을 시도하지 않고 "키가 없어 보류"로 가는데, 이번 건은 실제 제출이 나가 401을 받았다.

값 없이는 아래 세부 후보 중 어느 것인지 특정할 수 없다.

- 주소에 Signer Address가 아닌 주소 (예: 입금 지갑 주소)를 입력했다.
- 다른 Polymarket 계정으로 로그인한 상태에서 만든 키를 등록했다.
- 키 값을 옮겨 적는 과정에서 오타가 났다.
- 등록 후 Polymarket 설정에서 키가 삭제·폐기됐다.

앱 등록 화면의 주소 칸 안내가 "키 주소 (0x…)"로 모호해 첫 번째 후보를 걸러내지 못한 것은 앱 측 기여 요인이다.

## 키 발급 경로 (정본)

- 발급: polymarket.com → **Settings → API Keys → Relayer API Keys**에서 생성한다.
- 생성하면 **API Key**와 **Signer Address**가 표시된다. 앱에 넣어야 하는 값은 이 둘이다: 키 입력 칸에 API Key, 주소 칸에 Signer Address.
- Signer Address는 그 계정의 서명 지갑 주소로, 앱에 연동된 지갑 주소와 같아야 한다.
- 키 생성은 웹 로그인 (Gamma auth)으로만 가능하다. 앱이나 API 키만으로는 새 키를 만들 수 없다.
- 주소당 키는 최대 100개까지 만들 수 있다. 기존 키를 지울 필요 없이 새로 만들면 된다.

## 동호 절차 (재등록)

1. 앱에서 기존 키를 삭제한다: 자동 상환 (리딤) 카드 → 키 삭제.
2. polymarket.com에 **앱에 연동된 바로 그 계정** (@gigglyiguana6026)으로 로그인한다.
3. Settings → API Keys → Relayer API Keys에서 새 키를 생성한다.
4. 생성 직후 표시되는 **API Key**와 **Signer Address**를 그대로 복사한다 (Signer Address는 한 번만 표시될 수 있으니 그 화면에서 바로 옮긴다).
5. 앱의 자동 상환 (리딤) 카드에 키와 Signer Address를 입력하고 저장한다.
   - 이번에 넣은 등록 검증으로, 주소가 연동된 지갑 주소와 다르면 저장이 거부된다.
6. 다음 사이클부터 리딤 제출이 자동 재개된다. 성공 여부는 다음 제보의 로그에서 "리딤 회수"로 확인한다.

주의: 기존 키가 왜 거부됐는지는 Polymarket이 알려주지 않는다. 설정의 Relayer API Keys 목록에서 기존 키가 남아 있는지, 그 키에 표시된 Signer Address가 앱 연동 지갑과 같은지를 3번 단계에서 함께 보면 세부 원인을 좁힐 수 있다.

## 앱 측 조치 (구현 완료, 출시 대기)

자격증명 자체는 동호가 재발급해야 하지만, 같은 실패가 반복되지 않게 앱에 세 가지를 넣었다. 전부 JS·네이티브 패리티로 적용했다.

1. **등록 검증**: 키 저장 시 주소가 연동된 서명 지갑(EOA)과 다르면 저장을 거부한다. 주소 칸 안내를 "Signer Address (키 생성 시 표시된 주소)"로 바꾸고, 발급 경로를 폼 아래에 명시했다.
2. **401 래치**: 제출이 401로 거부되면 그 자격증명으로는 다시 제출하지 않는다. 종전에는 매 사이클 (약 78초 간격) 재제출하며 실패 로그·알림을 쌓고 relayer 일일 한도를 소모했다. 이제 하루 1회 보류 로그만 남기고, 키를 재등록하면 (자격증명 지문 변경) 자동으로 다시 시도한다.
3. **가드 테스트**: JS relayer-auth 18건 (401 판정, 지문, 소스 배선), 네이티브 NativeCycleTest에 auth401 래치 시나리오 6건 (첫 사이클 제출 1회, 같은 키 재제출 없음, 키 교체 시 재시도).
